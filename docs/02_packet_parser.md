# The Fast Path Ingress (`packet_parser.v`)

---

## 1. Purpose of the File

---

The file `rtl/parser/packet_parser.v` is the physical ingress point of the SmartNIC datapath. When raw pulses of light from the fiber optic cable are translated into digital bits by the 100G Ethernet MAC, those bits arrive precisely here.

### Why this file exists
Downstream modules (like the QoS Queues and Priority Scheduler) need to make instantaneous routing decisions based on IP addresses, TCP/UDP ports, and network slices. Forcing every downstream module to independently parse the raw binary packet payload is incredibly inefficient and consumes massive amounts of FPGA silicon logic.

### What problem it solves
This file solves the "parsing bottleneck." It acts as a specialized extraction engine. It rips open the first 64 bytes of every packet, identifies the protocol, extracts the IP addresses and ports, and packages them into a clean 128-bit `TUSER` metadata stamp. It then attaches this "shipping label" to the packet for the rest of its journey through the SmartNIC.

### Where it fits in the architecture
It sits directly behind the OpenNIC CMAC (Ethernet) subsystem and directly in front of the `flow_classifier.v`.

### What would break if this file disappeared
The entire SmartNIC would become blind. Without the metadata generated by this module, the Flow Classifier would not know which 5G Network Slice to route the traffic into, causing total datapath failure.

## 2. Background Theory

---

### A. Line-Rate Packet Parsing
In standard software networking (like Linux kernels), packets are parsed sequentially. The CPU reads the Ethernet header, decides it is IPv4, advances a memory pointer, reads the IPv4 header, decides it is UDP, advances a pointer, etc. This iterative state machine can take hundreds of clock cycles per packet.

At 100 Gbps, sequential parsing is mathematically impossible. A 64-byte packet arrives every 5 nanoseconds. The hardware must parse the *entire* header stack in a single clock cycle to achieve **Line-Rate** processing (processing data exactly as fast as the physical wire delivers it).

### B. The 512-bit Advantage
As defined in Chapter 1, our datapath uses a 512-bit (64-byte) wide bus. 
The standard network header stack is exactly 42 bytes:
* Ethernet II: 14 bytes
* IPv4: 20 bytes
* UDP: 8 bytes

Because 42 bytes is strictly less than the 64-byte bus width, **the entire protocol stack arrives simultaneously on the very first clock cycle**. This physical alignment allows us to bypass complex parsing trees entirely and use pure combinatorial logic.

### C. The `+:` Indexed Part-Select Operator
Verilog-2001 introduced the `+:` operator, which is heavily used in this file.
Instead of writing `data[31:24]`, you can write `data[24 +: 8]`. 
This means: "Start at bit 24, and select a width of 8 bits going upward." This is incredibly useful when parsing packets because you can parameterize the starting offset.

## 3. File Structure Walkthrough

---

The module is structured into distinct functional blocks:
1. **Module Interfaces:** Defines the AXI4-Stream Slave (input) and Master (output) ports.
2. **State Machine Definitions:** Defines an `IDLE`, `FIRST_BEAT`, and `FORWARDING` state.
3. **Pipeline Registers:** Defines the Flip-Flops that hold data between clock cycles.
4. **Combinational Header Extraction:** A massive block of continuous assignment wires (`assign`) that physically route bits from the input bus to specific protocol fields.
5. **TUSER Metadata Building:** Packs the extracted wires into the 128-bit standard format.
6. **Handshake Logic:** Manages the `TREADY` and `TVALID` backpressure signals.
7. **State Machine Execution:** The actual `always @(posedge clk)` block that moves data through the pipeline.

## 4. Line-by-Line Code Explanation

---

### The Module Interface
```verilog
    // â”€â”€ AXI-Stream Slave (Raw packets from CMAC/upstream) â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€
    input  wire [`AXIS_DATA_WIDTH-1:0]      s_axis_tdata,
...
    // â”€â”€ AXI-Stream Master (Packets with parsed metadata) â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€
    output reg  [`AXIS_DATA_WIDTH-1:0]      m_axis_tdata,
```
**What it does:** Defines the input and output pipes. The `s_` prefix denotes "Slave" (receiving data), while the `m_` prefix denotes "Master" (sending data). Notice that the Master interface includes an `m_axis_tuser` port, which does not exist on the input side.

### Combinational Extraction
```verilog
    wire [15:0] ethertype = {
        s_axis_tdata[(`ETH_ETHERTYPE_OFFSET * 8) +: 8],       // byte 12 (MSB)
        s_axis_tdata[((`ETH_ETHERTYPE_OFFSET + 1) * 8) +: 8]  // byte 13 (LSB)
    };
    wire is_ipv4 = (ethertype == `ETHERTYPE_IPV4);
```
**What it does:** Instantly evaluates the 13th and 14th bytes of the incoming packet.
**How it works internally:** The `{ }` concatenation operator joins two 8-bit slices into a 16-bit word. The `ETH_ETHERTYPE_OFFSET` macro (from Chapter 1) is `12`. `12 * 8 = 96`. So this logic permanently wires bits `[103:96]` and `[111:104]` to the `ethertype` bus.
**Why it exists:** If `ethertype` is not `0x0800` (IPv4), the module knows immediately that the rest of the extraction logic (IPv4 IPs, UDP ports) will contain garbage data.

### Metadata Construction
```verilog
    assign metadata[`TUSER_IS_IPV4_BIT]                         = is_ipv4;
    assign metadata[`TUSER_IS_UDP_BIT]                          = is_udp;
    assign metadata[`TUSER_DST_IP_HI:`TUSER_DST_IP_LO]         = is_ipv4 ? dst_ip : 32'd0;
```
**What it does:** Populates the `TUSER` sideband.
**Design Pattern:** Notice the ternary operator `? :`. If `is_ipv4` is true, the extracted destination IP is stamped into the metadata. If it is false, `32'd0` is stamped. This guarantees that downstream modules are never poisoned by parsing artifacts from unsupported protocols (like IPv6 or ARP).

### Handshake and Backpressure
```verilog
    wire output_handshake = m_axis_tvalid && m_axis_tready;
    wire input_handshake  = s_axis_tvalid && s_axis_tready;

    assign s_axis_tready = (state == ST_IDLE) ||
                           (state == ST_FORWARDING && m_axis_tready);
```
**What it does:** Ensures zero packet drops.
**Engineering Reasoning:** The module only asserts `s_axis_tready` (telling the upstream MAC it is ready to receive) if it is currently idle, OR if it is actively forwarding data and the downstream module is *also* ready (`m_axis_tready`). This creates a rigid interlocking chain. If the downstream Queue Manager stalls, this module stalls instantly, propagating the backpressure upstream.

### State Machine Transitions
```verilog
                ST_FIRST_BEAT: begin
                    if (output_handshake) begin
                        if (first_beat_last) begin
                            state <= ST_IDLE;
                        end else begin
                            state <= ST_FORWARDING;
                        end
                    end
```
**What it does:** Handles packet length variability.
**How data flows:** When outputting the first 64 bytes of the packet, it checks `first_beat_last` (which is a latched copy of the AXI `TLAST` signal). If `TLAST` is high, the packet was smaller than 64 bytes (e.g., a tiny TCP ACK). The packet is fully parsed and sent, so it returns to `IDLE`. If `TLAST` is low, the payload is larger than 64 bytes, and it transitions to `FORWARDING` to stream the rest of the payload using the same `TUSER` metadata.

## 5. Architecture Context

---

### What inputs arrive here
The CMAC Subsystem (Ethernet MAC) provides raw, unstructured Ethernet frames over the `s_axis` ports.
### What outputs leave here
The `m_axis` ports emit identical Ethernet frames, but with the critical addition of the fully populated `128-bit TUSER` metadata signal.
### Dependencies
This file depends exclusively on `smartnic_pkg.vh` for offset mapping. The output of this module feeds directly into `flow_classifier.v`.

## 6. Hardware Interpretation

---

### Datapath and Registers
The `always @(posedge clk)` block generates a vast array of D-Type Flip-Flops. Specifically, it registers exactly 512 bits for `first_beat_data`, 64 bits for `keep`, 1 bit for `last`, and 128 bits for `parsed_metadata`. 
This results in **705 parallel Flip-Flops** being physically etched into the FPGA silicon to act as the single-stage pipeline delay.

### Control Path
The state machine generates a tiny 2-bit register for the `state` variable (`ST_IDLE`, `ST_FIRST_BEAT`, `ST_FORWARDING`). The logic evaluating the next state is synthesized into combinatorial logic gates (LUTs) that feed the clock-enable pins of the massive 705-bit register array.

---

## 7. Design Decisions

---

### Why use a Pipeline Stage instead of Pure Combinatorial forwarding?
The architecture uses to latch the incoming data into a register (`first_beat_data`) rather than forwarding it immediately with an `assign` statement. 
* **Tradeoff:** This introduces exactly 1 clock cycle (4 ns) of latency.
* **Benefit:** It "breaks" the combinational logic path. The extraction logic (identifying IP addresses) and metadata mapping is mathematically complex and requires traversing many logic gates. If this was wired directly to the output, the logic propagation delay would be immense, and the FPGA would violently fail timing closure at 250 MHz. Registering the data grants the silicon a full 4 ns to calculate the metadata.

### Why not use a P4 Deparser approach?
Advanced programmable switches use the P4 language, which compiles into complex Match-Action tables and parsing graphs. While mathematically beautiful, P4 compilation to FPGAs is notoriously difficult and resource-intensive (as noted by Luinaud et al.). Because the 5G SmartNIC MVP only needs to support IPv4 and UDP, a hardcoded, static extraction matrix is infinitely faster and consumes a fraction of the silicon area.

## 8. Example Execution

---

**Scenario:** A 1500-byte IPv4 UDP packet arrives from the fiber.

1. **Cycle 1:** `s_axis_tvalid` goes high. The first 64 bytes arrive. The state machine is in `ST_IDLE`. The combinational wires instantly extract the IP addresses and determine it is UDP. On the rising clock edge, the 64 bytes are latched into `first_beat_data`, and the extracted metadata is latched into `parsed_metadata`. The state transitions to `ST_FIRST_BEAT`.
2. **Cycle 2:** The state machine outputs the latched 64 bytes and the `TUSER` metadata. `m_axis_tvalid` is driven high. Assuming the downstream classifier is ready (`m_axis_tready = 1`), the handshake succeeds. Because `first_beat_last` is 0 (it's a 1500 byte packet), the state transitions to `ST_FORWARDING`.
3. **Cycle 3 to 24:** The state machine is in `ST_FORWARDING`. The incoming 64-byte beats are routed directly to the output (`m_axis_tdata <= s_axis_tdata`). The `m_axis_tuser` remains permanently locked to the `parsed_metadata` generated in Cycle 1.
4. **Cycle 25:** The 24th beat arrives, bringing the total to 1536 bytes (satisfying the 1500 byte payload). The MAC asserts `s_axis_tlast`. The module outputs the final beat, the handshake succeeds, and the state transitions back to `ST_IDLE`, ready for the next packet.
